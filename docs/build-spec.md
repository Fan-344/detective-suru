# Detective Suru（暫名）｜開工規格 v0.1

最後更新：2026-11-14

工作分三步：先把第一案的文本寫完並架好手機外觀框架，再做一個能從開場玩到結局的文字冒險版來驗證玩法，最後才把兩者接起來。案件內容以 `docs/design.md` 為準。

## 1. 範圍與技術選型

先驗證玩法，再投入畫面。文字冒險版跑得通、玩起來有趣，才進入接畫面的階段。

### 三個步驟

1. **步驟一：文本與外觀框架（兩件事平行做）**
   - 文本：把第一案的全部內容寫成資料檔。十個 App 的內容、四個人的聊天紀錄、測試反應表、四條階梯每一級的訊息、助理的心聲、結局
   - 外觀框架：手機外殼。狀態列與電量、主畫面、進出 App，以及聊天室、清單、相簿三種版型。只接假資料，不含遊戲規則
2. **步驟二：文字冒險版**
   - 寫完 `engine` 的全部規則：電量、四條階梯、備忘錄比對、測試、登入確認視窗、挑戰書與結局
   - 一個文字介面，讀步驟一的資料檔，能從開場玩到任何一個結局
   - 自動檢查：每個關鍵結論到得了、每個結局觸發得了、沒有死路
3. **步驟三：接上畫面**
   - 把步驟一的外觀框架接到步驟二的 `engine`，補上備忘錄、測試面板、挑戰書等畫面

### 這份規格不包含的

- 正式圖像、音效、新手引導
- 第二案
- 任何即時呼叫 AI 的功能。對話全部是寫好的劇本
- 上架商店的包裝

### 技術選型

| 項目 | 選擇 | 理由 |
| --- | --- | --- |
| 形式 | 純前端網頁，沒有後端 | 不需要帳號和伺服器，成本接近零，方便匿名發行 |
| 框架 | Vite 加 React 加 TypeScript | 元件化適合做多個 App 畫面；型別檢查能擋掉資料格式的錯誤 |
| 狀態 | 單一的遊戲狀態物件，用 reducer 更新 | 所有變化走同一個入口，文字版和畫面版共用同一套邏輯 |
| 內容 | JSON 資料檔 | 劇情與程式分開，第二案只換資料 |
| 存檔 | 瀏覽器的 localStorage | 讀寫要包在 try/catch 裡，失敗時退回記憶體 |
| 測試 | Vitest | 跟 Vite 同一套工具 |
| 部署 | 靜態網站主機 | 建置後就是一包靜態檔案 |

這個專案開一個全新的 repo，跟其他專案分開。最重要的一條原則是遊戲邏輯不依賴畫面。

### 命名與外觀的限制

App 的名稱、圖示和介面都要是自己的設計，不仿製任何真實品牌。暫定名稱：聊聊（訊息）、片刻（社群動態）、找裝置、雲端發票、備忘錄、相簿、電話、簡訊、天氣。

## 2. 專案結構與資料格式

遊戲邏輯放在 `engine`，完全不碰畫面；畫面放在 `ui`，只讀狀態、送出動作。案件內容全部在 `content`。

### 目錄

```text
docs/
  design.md            設計文件（案件真相以此為準）
  build-spec.md        本文件
  voice/               每個角色的語氣指南（步驟一產出）
content/
  case01/
    meta.json          起始電量、各動作耗電、掩護說法
    characters.json    人物、語氣、階梯
    apps.json          App 清單與排列
    items.json         所有可以被看到的東西（紀錄與說法）
    threads.json       聊天室與舊訊息
    links.json         說法對紀錄的比對結果
    cards.json         測試牌
    reactions.json     牌 × 對象的反應表
    conclusions.json   關鍵結論與備援路徑，供自動檢查用
    voice.json         助理的心聲
    endings.json       結局
    assets/            圖片
src/
  engine/              狀態、reducer、規則。不得引用 React
  ui/                  外殼與各 App 畫面
  content/             載入器與格式檢查
tools/
  play.ts              文字模式執行器
  validate.ts          內容檢查：每個結論到得了、沒有死路
```

### reactions.json

```json
[
  {
    "card": "card_latte",
    "target": "aze",
    "when": { "ladder": { "aze": { "min": 1 } } },
    "reply": ["……", "你幹嘛現在講這個", "好啦我們有見面"],
    "reveals": ["say_aze_admit"],
    "effects": { "ladder": { "aze": 1, "jingwen": 0 } }
  }
]
```

沒有對應的組合一律回到該角色的通用反應（一頭霧水），所以表只需要寫有內容的那幾格。

### conclusions.json

```json
[
  {
    "id": "aze_met_her",
    "text": "阿澤週六其實見過以晴",
    "routes": [["rcp_1842"], ["say_aze_ok", "say_aze_stoodup"], ["say_aze_admit"]]
  }
]
```

每條主線結論至少兩條 `routes`。`validate.ts` 會檢查這一點，也會檢查每條路上的 item 都真的拿得到。

## 3. 系統規則與畫面清單

所有規則都寫在 `engine` 裡，輸入一個狀態和一個動作，輸出新的狀態。畫面和文字版共用。

### 遊戲狀態

```json
{
  "battery": 64,
  "seen": ["rcp_1842"],
  "ladder": { "jingwen": 1, "aze": 0, "zonghan": 0, "pinyu": 1 },
  "threads": { "dm_aze": { "appended": [] } },
  "links": [],
  "cardsUsed": [],
  "ended": null
}
```

### 玩家能送出的動作

| 動作 | 耗電（暫定） |
| --- | --- |
| 第一次打開某個 App | 1 |
| 第一次讀某個聊天室 | 1 |
| 送出一則訊息（選項式） | 2 |
| 用找裝置定位 | 4 |
| 在備忘錄比對一組說法和紀錄 | 0 |
| 拿一張牌測試某個人 | 2 |
| 回應登入確認視窗 | 0 |
| 提交挑戰書 | 0 |

重複打開已經看過的東西不耗電。

### 電量

- 起始 64%，只會減少，沒有充電、沒有省電模式
- 歸零就結束
- 每掉 8%，沒有被安撫的角色階梯自動加一級

### 階梯

- 每個角色一個整數等級。進入新等級時執行該級的 `onEnter`
- 等級由兩件事改變：玩家送出的訊息帶有的 `effects`，以及電量每掉一段的自動推進
- 有些 item 只在某個等級的 `onEnter` 裡才會出現
- 畫面上不顯示等級數字，只顯示行為：已讀時間、輸入中的提示、訊息長短
- 靖雯到第六級（查到醫院）即結束

### 備忘錄與測試

- 看過的 item 自動進備忘錄，依 `kind` 分成紀錄與說法兩欄，另有一條依時間排序的時間軸
- 玩家選一則說法和一筆紀錄做比對。`links.json` 有這一組就回傳吻合或矛盾，沒有就回傳「看不出關聯」
- 矛盾的比對會解鎖對應的測試牌
- 測試：選一張牌、選一個對象，從 `reactions.json` 找符合條件的反應；找不到就用該角色的通用反應
- 助理的心聲：每個關鍵結論三級提示，該結論遲遲沒被摸到（以電量消耗計）才升級

### 挑戰書與結局

- 四個欄位：動機、不在場證明怎麼破、手法、在場證明。每一欄從已取得的紀錄中選
- 再選擇交給誰：品妤、宗翰、阿澤
- 結局判定規則見 `docs/design.md` 第 7 節

### 畫面清單

| 畫面 | 內容 | 步驟 |
| --- | --- | --- |
| 開場 | 黑底文字，逐段顯示，點一下前進 | 一 |
| 主畫面 | 狀態列、App 格子、未讀紅點 | 一 |
| 聊聊：列表 | 群組和四個私訊，顯示最後一句 | 一 |
| 聊聊：聊天室 | 舊訊息、底部的回覆選項 | 一 |
| 清單加詳情（發票、簡訊、電話、天氣） | 依日期分組的清單，點開看內容 | 一 |
| 相簿 | 縮圖格子，點開看大圖和時間 | 一 |
| 沒電 | 螢幕變暗，回到開場 | 一 |
| 備忘錄 | 時間軸、紀錄欄、說法欄、比對、手上的牌 | 三 |
| 測試面板 | 選牌、選對象、預覽要送出的句子 | 三 |
| 系統視窗 | 登入確認 | 三 |
| 挑戰書與結局 | 四個填空、選擇交給誰、結局文字 | 三 |

### 手機畫面的要求

- 只支援直式。橫放時顯示請轉回直式
- 高度用動態視窗單位，避開瀏覽器網址列造成的跳動
- 留出瀏海和底部橫條的安全區域
- 桌面瀏覽器打開時，在畫面中央顯示一個手機尺寸的框
- 第一版沒有自由輸入，所以不會彈出鍵盤

## 4. 各步驟的任務與驗收

每個步驟有自己的任務和通過標準。沒通過就停在那一步改，不往下做。

### 任務

**步驟一：文本**

- [ ] 建立專案骨架，定義資料型別，寫載入器和格式檢查
- [ ] 每個角色寫一頁語氣指南：用詞、訊息長短、表情符號、怎麼稱呼以晴，各附十句範例
- [ ] 十個 App 的靜態內容：簡訊、備忘錄、發票、相簿（先用文字描述圖片）、通話、私訊、群組、片刻、天氣、找裝置
- [ ] 開局的掩護說法，以及送出後四個人在群組和私訊的第一輪反應
- [ ] 測試牌清單和反應表，含每個角色的通用反應
- [ ] 四條階梯每一級的訊息，含玩家不同回覆下的升降
- [ ] 助理的心聲，每個關鍵結論三級
- [ ] 挑戰書的選項和各結局的文本
- [ ] `conclusions.json`：每個關鍵結論至少兩條路

**步驟一：外觀框架**

- [ ] 手機外殼：狀態列與電量、主畫面的 App 格子、未讀紅點、進出 App 的轉場
- [ ] 三種版型：聊天室、清單加詳情、縮圖格子加大圖
- [ ] 開場畫面和沒電畫面
- [ ] 自己的 App 名稱與圖示，不仿製真實品牌
- [ ] 部署一個可以用手機打開的預覽網址

**步驟二：文字冒險版**

- [ ] `engine`：狀態、動作、reducer、電量扣除
- [ ] 四條階梯：等級變化、`onEnter` 事件、電量每掉一段自動推進
- [ ] 備忘錄：紀錄與說法兩欄、比對、產生測試牌
- [ ] 測試：選牌、選對象、套用反應表
- [ ] 登入確認視窗、挑戰書、結局判定
- [ ] 文字介面：列出可做的動作、輸入編號執行、印出結果和剩餘電量。終端機和網頁各一個入口，網頁版方便傳給朋友試玩
- [ ] `validate`：自動模擬各種玩法，檢查結論、結局、死路

**步驟三：接上畫面**

- [ ] 外觀框架改讀 `engine` 的狀態、送出動作
- [ ] 備忘錄、測試面板、系統視窗、挑戰書與結局畫面
- [ ] 存檔與讀檔

### 驗收條件

**步驟一通過的標準**

1. 資料檔全部通過格式檢查，故意改壞一筆會看到清楚的錯誤訊息
2. 把四個人的訊息遮掉名字，讀的人分得出是誰說的
3. 文本裡沒有任何一句跟設計文件的案件事實矛盾
4. 外觀框架在 iPhone 的 Safari 和 Android 的 Chrome 上直式打開不跑版，能進出三種版型

**步驟二通過的標準**

1. 文字版能從開場玩到每一個結局
2. `validate` 全部通過
3. `engine` 資料夾裡沒有任何畫面相關的引用
4. 找三到五個沒看過設計文件的人試玩，用下面三個問題檢查

**每次試玩都要問的三個問題**

1. 玩家有沒有卡住、需要停下來想的地方
2. 有沒有人指錯兇手
3. 兩個人玩的過程是否不一樣

三題有任何一題的答案是「沒有」，代表遊戲滑回「線性地聽故事」，要先改設計再往下做。

### 之後

| 之後 | 內容 |
| --- | --- |
| 步驟三完成後 | 正式圖像、音效、新手引導 |
| 發行前 | 第一案免費放出，看有沒有不認識的人玩完並在網路上談論 |

## 5. 給 Claude Code 的開場白

把 `design.md` 和這份規格放進 repo 的 `docs/` 之後，整段貼上當第一則訊息。建議開三個對話，分別負責文本、外觀框架、文字冒險版，最後一行各填一個。文本和外觀框架可以同時進行，文字冒險版等文本的資料格式定下來再開始。

```text
這個 repo 要做一款手機直式的網頁推理遊戲，暫名 Detective Suru。玩家是一支手機裡的 AI 助理 Suru，主人昏迷住院，推她的人不確定自己有沒有得手，正在試探「她」。玩家要假扮主人回訊息，在電量用完前找出兇手。

請先讀這兩份文件，再動手：
- docs/design.md：設計文件。人物、真相、線索、結局都以它為準
- docs/build-spec.md：開工規格。技術選型、目錄、資料格式、三個步驟的任務與驗收

工作順序：
1. 步驟一：把第一案的文本寫成資料檔，同時架好手機外觀框架
2. 步驟二：做一個能從開場玩到結局的文字冒險版
3. 步驟三：把外觀框架接上遊戲邏輯

這次對話負責的部分寫在最後一行。只做那一部分。

規則：
1. 劇情內容一律放在 content/case01/ 的資料檔，程式裡不寫死任何台詞或線索
2. src/engine 不得引用任何畫面相關的東西。畫面和文字版共用同一套邏輯
3. 不加任何即時呼叫 AI 的功能
4. 不要更動 docs/design.md 裡的案件事實。發現矛盾或缺漏，列出來問我，不要自己補
5. 寫文本時，先為每個角色寫語氣指南給我確認，再寫訊息。四個人講話要分得出來，用台灣人傳訊息的口氣，繁體中文，不用中國用語
6. 旁白和助理的心聲只提問、不替玩家下結論
7. App 的名稱、圖示、介面用自己的設計，不仿製真實品牌
8. 要加新的套件之前先說明理由
9. 以手機直式為準，桌面只要置中顯示一個手機尺寸的框
10. 每完成一項任務就跑一次建置和測試，並告訴我怎麼看成果

開始前請先回覆三件事：你對這次範圍的理解、打算採用的做法、以及文件裡你覺得不清楚或互相矛盾的地方。等我確認後再動手。

所有回覆請用繁體中文。

這次對話負責：（擇一填入）步驟一的文本／步驟一的外觀框架／步驟二的文字冒險版
```

## 6. 遊戲的開場白（初稿）

從助理醒來到玩家送出第一則訊息為止。黑底白字，一段一段出現，點一下前進。這是初稿，用來定語氣。

### 文本

```text
［螢幕亮起］

電量 64%
Wi-Fi：快修通訊_5G

你醒了。

沒有人拿起手機。沒有人說話。
叫醒你的，是一條兩天前設定的指令。

————
如果我兩天沒回來解鎖，你就醒來。
先不要讓任何人知道你在。
今晚我要一個人去問一個人一件事。
我不確定對方會怎麼反應。
```

### 這段開場要做到的事

- 身分和規則直接講：你是誰、她交代了什麼
- 現況讓玩家自己拼：醫院簡訊加未接來電，文本不替玩家下「她被人害了」的結論
- 指令只說今晚要一個人去問一個人一件事，不說是誰、不說是什麼事。她指的是宗翰和押金，但玩家一開始分不出來。代名詞刻意不用他或她
- 最後一句埋下電量這個上限
- 醫院名稱先用○○，寫文本時要取一個虛構的名字，不用真實醫院
